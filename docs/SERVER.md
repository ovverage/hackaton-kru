Обновление сайта само по себе не обновит установленный клиент: нужен установщик 0.4.5 или новый переносимый EXE. История развёртываний и проверок — в [VERIFICATION.md](VERIFICATION.md).

## Доступ

Имя преподавателя: `admin`. Отдельный пароль создан при развёртывании; он находится в локальном игнорируемом файле `.local/deploy/admin-initial.json` и резервном файле `/etc/qorgau/initial-admin.json` на сервере с правами `0600`. Пароль SSH не используется для кабинета. Не добавлять эти файлы в Git и не переносить пароли в эту инструкцию.

Учётная запись создана до публикации сайта. Внешние `/api/auth/setup`, `/docs`, `/redoc` и `/openapi.json` закрыты на прокси. Пароли пользователей хранятся в БД в виде Argon2-хешей. Сессия кабинета использует cookie Secure, HttpOnly и SameSite Strict.

API слушает только адрес внутреннего Docker-моста. UFW разрешает вход на него от текущего IP контейнера Caddy `172.19.0.4`. Только этому адресу Uvicorn доверяет заголовки прокси. При смене сети или IP контейнера одновременно обновить адрес прослушивания, правило UFW, `--forwarded-allow-ips` в службе и upstream Caddy. Не открывать порт 8765 на публичном интерфейсе.

Используется один worker Uvicorn: текущие WebSocket-снимки, ограничитель входа имеют состояние в памяти. Дополнительные worker-процессы требуют отдельной проверки архитектуры.

Существующие сайты сохранены. Для Qorgau добавлены блоки IP и `default_sni 212.19.134.23` в глобальную секцию: TLS-клиенты при обращении к IP не передают обычный SNI. Caddyfile обновлён в работающем контейнере; в Compose добавлено чтение этого файла с хоста при следующем пересоздании контейнера. Контейнеры других проектов не перезапускались.

## Повседневные команды

Выполняются через SSH на сервере:

```sh
sudo systemctl status qorgau --no-pager
sudo journalctl -u qorgau -n 60 --no-pager
sudo systemctl restart qorgau
curl --fail https://212.19.134.23/api/health
sudo systemctl list-timers 'qorgau*' --no-pager
df -h /
```

Служба включена в автозапуск, автоматически перезапускается после завершения процесса и работает с отдельными правами на каталог данных. Ограничение памяти — 768 МБ. Полную перезагрузку общего сервера при установке не выполняли.

## HTTPS и продление

Сертификат выпущен с профилем `shortlived`; первый экземпляр действует до **12 октября 2026 года 16:25 по времени Asia/Qyzylorda**. Короткий срок требует работающего автоматического продления.

`qorgau-certificate.timer` запускает проверку дважды в сутки, в 00:15 и 12:15 UTC со случайной задержкой до 20 минут. Certbot использует HTTP challenge по порту 80. Маршрут `/.well-known/acme-challenge/` должен оставаться доступным; остальной HTTP перенаправляется на HTTPS.

После продления `/usr/local/sbin/qorgau-renew-hook` копирует сертификат и закрытый ключ в постоянный volume и выполняет принудительное обновление конфигурации Caddy. Ключ имеет права `0600` и не находится в веб-каталоге. Пробное продление прошло успешно.

```sh
sudo /opt/qorgau/certbot/bin/certbot certificates --cert-name qorgau-ip
sudo /opt/qorgau/certbot/bin/certbot renew --cert-name qorgau-ip --dry-run
sudo journalctl -u qorgau-certificate.service --no-pager -n 40
```

Справка: [официальная инструкция Let's Encrypt для IP и Certbot](https://letsencrypt.org/2026/03/11/shorter-certs-certbot), [настройка default_sni в Caddy](https://caddyserver.com/docs/caddyfile/options#default-sni).

## Резервное копирование и восстановление

`qorgau-backup.timer` запускается ежедневно в 03:30 UTC с задержкой до 15 минут. Скрипт использует SQLite Backup API, проверяет целостность снимка и добавляет только видео, на которые ссылается этот снимок. При недостатке места копирование завершается ошибкой; старые копии удаляются только после успешного создания новой. Сохраняются 7 архивов.

```sh
sudo systemctl start qorgau-backup.service
sudo journalctl -u qorgau-backup.service --no-pager -n 10
sudo ls -lh /var/backups/qorgau/
```

Копии по расписанию находятся на том же сервере: они защищают от ошибки обновления, но не от потери самого диска. Для постоянной защиты требуется отдельное внешнее хранилище. Первоначальная копия дополнительно сохранена на компьютере пользователя в `.local/deploy/qorgau-initial-backup.tar.gz`.

Порядок восстановления:

1. Выбрать архив и распаковать в отдельный временный каталог; проверить `PRAGMA integrity_check` и наличие всех видео.
2. Остановить `qorgau.service`. Сохранить текущий каталог `/var/lib/qorgau` под отдельным именем для отката; не накладывать БД поверх старых WAL-файлов.
3. Создать новый `/var/lib/qorgau`, перенести восстановленные БД и `media`, назначить владельца `qorgau:qorgau` и закрытые права доступа.
4. Запустить службу, проверить вход, устройства, отчёты и видео. При переносе в другой каталог учесть абсолютные пути медиа в таблице `media`.

После обновления 0.4.0 архив `qorgau-20261006T133108544681Z.tar.gz` восстановлен в отдельный временный каталог: `integrity_check=ok`, новая таблица `unlock_attempts` присутствует, SHA-256 всех пяти клипов совпали. Рабочая БД этим тестом не заменялась. Свидетельство: `docs/evidence/backup-0.4.0.json`.

## Обновление приложения

1. Пройти тесты и собрать `web/dist`. Сформировать новый каталог выпуска из `backend`, `shared`, `deploy`, `web/dist`, `requirements-core.lock` и `dist/Qorgau-Student.exe`. Не отправлять `.local`, токены, `.env`, записи и локальную БД.
2. Создать резервную копию текущей БД и проверить её. При изменении зависимостей сохранить прежнее Python-окружение для отката и подготовить отдельное новое.
3. Загрузить новый выпуск в `/opt/qorgau/releases/<версия>`, проверить права и конфигурацию. Учётную запись преподавателя повторно не создавать.
4. Атомарно переключить ссылку `/opt/qorgau/current`, перезапустить только `qorgau.service`, проверить HTTPS, вход, WebSocket, EXE и клип. Не пересоздавать остальные Docker-сервисы ради обновления Qorgau.
5. Если запуск неуспешен, вернуть предыдущую ссылку и окружение. При несовместимой миграции БД восстановить предшествующий снимок по отдельной процедуре, сохранив текущие данные для разбора.

Фактические версии установленных зависимостей записаны в `/opt/qorgau/venv-installed.lock` и `/opt/qorgau/certbot-installed.lock`. Шаблоны служб и настройки этого конкретного сервера находятся в `deploy/`; перед переносом на другой хост заменить адреса, сеть, имена контейнеров и пути томов.

## Проверки и ограничения

Результаты перечислены в `docs/VERIFICATION.md`. В кабинете оставлен явно обозначенный тренировочный сеанс с синтетическим роликом и тестовые регистрации, чтобы результат проверки можно было осмотреть. Ни одно из этих событий не является наблюдением за реальным студентом.

Сервер: 2 CPU, около 8 ГБ RAM, диск 24 ГБ. После обновления 0.4.0 замерено 7 189 786 624 свободных байта (около 6,7 ГиБ); это моментальный замер, а не квота хранения. Вместимость архива для 50 ПК не подтверждена. Перед пилотом измерить расход видео и предусмотреть требуемый объём диска или отдельное хранилище.

`PROCTOR_MEDIA_RESERVE_BYTES=536870912` запрещает запись новых порций видео, если нарушается резерв 512 МиБ; API отвечает 507 и удаляет незавершённый файл. Само событие сохраняется и допускает повторную загрузку. Это проверяется тестом.

## Сроки видео и отзыв устройства

`qorgau-retention.timer` запускается ежедневно в 04:15 UTC с задержкой до 15 минут. Он удаляет видео завершённых экзаменов старше 7 дней, сохраняя события и аудит. Продление с причиной доступно в карточке события. Активные сеансы и продлённые записи не удаляются. Пробный запуск новой службы успешен; тесты удаления используют изолированные синтетические данные.

```sh
sudo systemctl status qorgau-retention.timer
sudo journalctl -u qorgau-retention.service --no-pager -n 20
sudo -u qorgau /opt/qorgau/venv/bin/python -m backend.proctor.retention --data /var/lib/qorgau --days 7
```

Последняя команда — предварительный просмотр; для применения требуется `--apply`. Запускать из `/opt/qorgau/current`. Архивы резервных копий хранятся отдельно до ротации семи успешных копий. Отзыв ранее подключённого ПК выполняется в разделе «Компьютеры» с причиной после завершения его сеанса; его токен становится недействительным. Отзыв пакета аудитории и отзыв устройства — разные операции.

Для отката сохранены `20261006-cv-05`, `20261006-cv-04`, `20261006-cv-03`, `20261006-cv-02` и `20261006-server-01`. Не редактировать существующие файлы выпусков на месте: неизменяемые файлы CV-выпусков могут быть hard links для экономии диска. Создавать новый выпуск, а заменяемые файлы записывать через новый inode. Удалён только собственный промежуточный upload-архив после сверки SHA-256; локальная копия сохранена.

Предыдущий выпуск `20261006-cv-06` сохранён для отката. Объединённая версия развёрнута как `20261006-combined-040`; финальные документы и архивы добавлены отдельным выпуском `20261006-combined-040-docs` с тем же EXE и кодом сервера. Манифест содержит commit исходников, признак чистого рабочего дерева, размеры и SHA-256 всех пяти артефактов. В 0.4.0 раздача выполнялась через подготовленные пакеты.
